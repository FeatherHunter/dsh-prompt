# 远程大面板不设固定 px 尺寸，取「锚点上方全部可用高度 + 内部相对缩放」

远程模式的诉求是「在手机上通过 UU远程操作 4K / 2K / 1080P 桌面时，拿远了也点得中」。UU远程把整屏**等比缩放**到手机屏，插件拿不到「手机屏物理尺寸」与「串流缩放比」这两个量，因此任何以绝对 px 表达的「大」，都是对一个观测不到的缩放比的猜测：写死 860px 在 1080p 量级的窗口里看着像满屏（860 ≈ 1080 的 80%），到 4K（2160 高）只占 40%，再经串流缩一次——正是本功能要治的病，只是被原地复现了一遍。故本插件远程大面板的尺寸一律由**可用空间**导出：高度取 Prompt 按钮顶边以上的全部可用高度、宽度近全宽；面板内部所有尺寸（字号 / 行距 / 图标 / 底栏键高 / 槽间距）以面板尺寸为基准缩放，代码中不出现绝对 px 常量。「字号 / 控件」三档只是这个自动基准之上的**乘数**，故「与分辨率解耦」是构造性成立，而不是一句承诺。同一策略在「全桌面适配」与「1:1 原始比例」两种串流下，都给出该模式下的最大绝对尺寸。**这不是「越大越好」的审美偏好，而是唯一不依赖未知量的选择。**

**状态**：accepted（2026-09-29，map #78 / 规格 #85 / 实现 #83 / 验收 #84）。串流前提已由用户同日确认：UU远程为**全桌面适配**（整块桌面画面按屏等比缩放播放），故屏占比是不变量，本决策的直接依据成立；若日后改在 1:1 原始比例下使用，本决策仍需重新审视（见「后果」）。

## 考虑过的选项

- **沿用原型的固定 px**（面板高 `Math.max(420, Math.min(860, room))`、卡片字号 18 / 16 / 15、底栏键 104、TAB 行 68）—— 在原型被审阅的那块视口里视觉正确，但它把「当时那块屏」固化进了代码：860 在 1080p 量级像满屏，到 4K 只剩 40% 高。已明令作废（#85「尺寸规范」）。
- **按分辨率写六套常量**（横竖 × 4K / 2K / 1080P）—— 六格是**验收矩阵**，不是实现矩阵。写六套常量等于六份会各自漂移的布局，且任何未列出的视口（窗口化、系统缩放 125%、超宽屏）都掉进未定义行为。
- **按 `vh` 的固定比例**（如恒取 0.88vh）—— 比例本身仍是猜。面板高度真正的天花板是**按钮顶边**（既有定位是 `bottom = vh − btn.top + 8`），不是视口高度；两者不等，取固定比例会在输入条变高时溢出。
- **取锚点上方全部可用高度 + 内部相对缩放（选定）**—— 与缩放比无关，六格与未列出的视口共用同一套公式；代价是卡片尺寸随视口浮动，写测试时不能再用「第 N 号卡片多宽」这类绝对断言。

## 后果

- 尺寸断言必须**自相对**：可断言的是「面板占满可用高度」「代码中无 px 常量」「12 槽恒定、不减行」，而不是「面板宽 1600」。44px 触控目标降为**告警断言**（六格内不应触发），不作布局分支。
- **「一屏十二槽在手机上全可见」不是本决策能保证的事**：插件观测不到手机的可视窗口。该断言只能在真机由人判定，且**必须记录当时使用的 UU 显示模式**；若为「1:1 原始比例」，该承诺不成立（#85「前置假设与验收口径」）。
- 「12 槽恒定、卡片收缩」直接否决了原型的 `while(rows>1 && gridH/rows<110) rows--` 减行逻辑——减行会破坏「固定十二槽 + 高度稳定」这条冻结骨架。
