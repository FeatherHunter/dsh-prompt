# 不引入反斜杠转义语言：正文保留首尾换行，光标用 {{cursor}} 标记 + 宿主两编辑落位

**状态**：accepted（#178 拍板，2026-10-29；#181 修订落位与撤销分组，2026-10-29）

## 背景

[#178「对转义符的支持」](https://github.com/FeatherHunter/dsh-prompt/issues/178)（外部报告者 kBlankii）提了两件正交的事：**R1** 正文里写 `\n`，希望插入后是换行而不是字面反斜杠+n；**R2** 正文里放一个特殊符号，插入后光标停在该位置、文本里不留符号。事实清单见 `research/template-escape-caret/findings.md`（2026-10-28，只认本仓源码与本机宿主的抽取源码）。关键事实：

- **真换行本来就能存能插**：#76 已修掉「点模板注入吞尾部空行」，回归 `scripts/repro/test-issue-76.cjs` 22 个用例覆盖空行、尾部空行、光标处注入；正文编辑弹窗是多行 textarea，中间换行与空行保存后原样落库。R1 的真实卡点只有一处：保存时 `body.trim()` 把**首尾**空白（含换行）削掉。
- **R2 没有现成的宿主 API**：本机 DSH 0.2.1-rc.3 的公开 `InputActions` 只有 `setDraft` / `captureInsertion` / `insertText`，没有 `setCaret` / `setSelection`；`setDraft` 的语义是整框替换且光标置尾。R2 只能靠「可撤销的纯文本编辑」把光标留出来。
- **反斜杠转义会伤存量**：插入期把字面 `\n` 解码成换行，对存量正文里本该是字面反斜杠+n 的内容（Windows 路径 `C:\new`、正则 `/\n/`、代码片段）是不可逆改义；`\\` 只能保护「今后按新语法书写」的数据，保护不了存量。这与本仓「用户数据逐字节不变」的价值观冲突（`docs/adr/0007-template-color-is-user-data.md` 是同一类边界：用户数据永不翻译、永不改写）。
- **能力优先**：真换行与光标定位本来就是该有的能力，不该让用户先学一门转义语法。本仓不接受为补宿主能力而给字符串加第二套语义。

## 决定

### 1. R1：不引入反斜杠转义语言，只放宽保存时的 trim

- 模板正文保存时**只削首尾空格与 tab**，保留所有换行，包括正文开头与结尾的空行。
- 保存 → 重开 → 再存**幂等**：不会越存越短，也不会把空行吃掉。
- **存量正文逐字节不变，不做迁移**：不解析、不重写、不「顺手把存量里的字面 `\n` 转成真换行」。字面 `\n` 在正文里就是两个字符。
- 读取面按真换行的语义收敛（只归一显示，不写回）：列表首行简介取**第一个非空行**（空首行不再出空简介）；单行预览把连续空白压成一个空格；搜索 haystack 与智能评分用**剥掉标记后的正文**。

### 2. R2：正文里第一个 `{{cursor}}` 是插入后的光标目标

- 识别规则：正文里**第一个** `{{cursor}}` 的位置就是插入后光标的位置；插入文本里**所有** `{{cursor}}`（含第一个）都删除。它是正文语法里唯一新增的字面标记，不参与任何其他解码；选它是因为花括号串在 prompt 正文里罕见、在编辑框里看得见、不撞路径/正则等字面文本。
- 落位手法（宿主 0.2.1-rc.3 的公开面上）：第一笔 `insertText(正文含一个标记, { start, end, draftRev })` 把标记落在目标位（折叠光标处），再 `captureInsertion()` 取新 `draftRev`，第二笔 `insertText('', { start, end, draftRev })` 删掉标记。Lexical 删除文本后光标塌缩在删除区间的起点 ⇒ 光标精确落在标记处、标记消失。两次编辑只在同一个同步任务内存在，用户看不到中间态。**（v1 的第一笔是 `setDraft(含标记全文)`；#181 证明它会与插入前的输入共用一条撤销记录，已废弃，见 §3。）**
- 降级阶梯（任何一环不可用都落到安全路径，**文本永远正确**）：
  - 无标记 → 单笔 `insertText(正文, 折叠光标)`，光标落在插入文本之后（#181 显式接受的契约变更）；
  - 光标非折叠 / `captureInsertion` 坐标与插件落点不一致 → 整框 `setDraft`，光标置尾；
  - 草稿含引用 chip → 剥标记 + 整框 `setDraft`，光标置尾；
  - 旧宿主缺 action / `insertText` 返回 `false` / 抛错 → 剥标记 + 整框 `setDraft`，光标置尾；以上任何降级分支都记 `mode=degraded`；
  - `/prompt` 斜杠插入：插件只回文本、拿不到替换后的光标，**只剥标记、不定位**。
- 无标记时插入文本与旧版**逐字符一致**，唯一变化是光标落在插入文本之后（不再由宿主置草稿尾）；标记在所有展示面（列表简介、单行预览、搜索、`/prompt` 候选）都不出现。

### 3. #181：用户意图写入必须走可撤销编辑原语，`setDraft` 只做 seed 与降级

- 真机现象（#181，dsh-prompt 0.4.39 + 宿主 0.2.1-rc.3，3/3 复现）：草稿 `abc` 里插入含标记模板，插入后第一次撤销把标记文本恢复出来（符合预期），**第二次撤销把插入前的 `abc` 一起撤掉**，草稿清空。数据丢失。
- 根因在宿主源码里可读：宿主有两条公开写原语，undo 分组语义相反。
  - `setDraft` 走 `history-merge` 标签：**无条件并入当前那条历史记录**（没有时间窗、不看输入类型），是「整框 seed」，本身不是独立可撤销步。
  - `insertText` 走 `paste` 标签：**强制独立成一条 undo**（forceHistoryPush），并会切断后续输入的合并窗口。
  - 因此第一笔用 `setDraft` 的插入，会和用户插入前的输入焊在同一条撤销记录里；「再按一次撤销插入」实际撤的是「插入前的输入 + 插入」。原语选错，不是宿主 bug。
- 现行落位手法（两笔都是可撤销的 paste 记录，顺序在同一同步任务内）：
  1. `captureInsertion()` 取折叠光标处的 `{ start, end, draftRev }`，要求 `start === end === 落点`（否则降级）；
  2. `insertText(正文含一个标记, { start, end, draftRev })` —— 第一笔独立 undo；
  3. 再 `captureInsertion()` 取新 `draftRev`；
  4. `insertText('', { start: markerAt, end: markerAt + 标记长, draftRev })` 删标记 —— 第二笔独立 undo；Lexical 删除后光标塌缩在删除区间起点，标记消失、光标精确落位。
- 由此 undo 序列变成：**undo1 撤「删标记」（标记文本回到正文），undo2 撤整段插入、回到插入前的草稿**；无标记路径则 undo1 直接回到插入前草稿。两条路径的插入本身都是独立可撤销编辑。
- 无标记路径：单笔 `insertText(正文, 折叠光标)`，光标落在插入文本之后，不再由宿主置草稿尾（行为变化，中英 README 同步写清）。
- **不变量（门禁 `check:issue-181` 钉住）**：非降级路径（`mode = span | plain`）**不得调用 `setDraft`**；`setDraft` 只用于降级（`mode = degraded`）。空草稿的宿主 seed 不在本决定范围内。
- 修法候选与取舍（A 已采用）：
  - **A. 纯 paste 两编辑（采用）**：只依赖宿主现有公开 API，不改宿主、不改引擎；代价是插入本身变成两笔独立撤销记录（undo1 先撤「删标记」），净值是数据不再丢。
  - **B. 假 paste 边界 + 保留 `setDraft`（回退项，记为有意负债）**：先用一笔瞬时 `insertText` 把当前 history 顶成新记录，再 `setDraft` 让 `history-merge` 并入这条假记录。能修掉吞草稿，但会多一次可见草稿变更（`draft-changed`/持久化/闪动风险），还要绕过 `setDraft` 的「文本未变即 return」短路。**只有 A 在某类宿主上被证伪时启用**；移除条件：上游补了带 history 选项的 `setDraft` 或带光标参数的 `insertText`，届时回到单编辑路径（见「考虑过的选项」里的上游 API 一条）。
  - **C. 上游加 API**：最干净，但需版本门槛 + 旧宿主降级，记为将来方案，不阻塞本决定。
  - **D. 只写文档**：否决 —— #181 的代价是数据丢失，不是可接受的 UX 妥协；v1 文档只写了 undo1 露标记，没有写 undo2 吞草稿，补写也不改变损失。
- **Step 0 真机判定（A 是否真机可行）**：待真机验收回填 —— 需确认 (i) `captureInsertion` 的 detect 坐标与 `resolveDraft` 落点一致（否则一律降级、A 退化为文档口径）；(ii) 多行正文经 `insertText` 插入后，渲染/提交/持久化与 `setDraft` 按段切的模型等价（换行逐字符保真）；(iii) 真机 undo1/undo2/undo3/redo 序列与本节描述一致；(iv) 降级支路可达性与文本正确。若 (i) 或 (ii) 不成立，A 对「有标记 + 多行」退化为 B 或降级路径，须在实施记录中标注。

### 4. 已知代价写进用户文档，不藏

- 插入后**第一次撤销可能把标记文本恢复出来**（两次 paste 编辑在宿主里是两步），再按一次撤销插入、回到插入前的草稿；无标记插入第一次撤销即回到插入前的草稿。修复前第二次撤销会把插入前的输入一起吞掉（#181），该数据丢失已消除。
- 字面 `{{cursor}}` 文本暂时无法表达（要让这串字符本身落进正文，目前没有语法）。
- `/prompt` 路径不承诺光标落位（宿主负责替换，插件没有二次动作机会）。

## 考虑过的选项

- **插入期 `\n` 解码** —— 只改「插入瞬间」的文本；存量里本就要字面反斜杠+n 的内容（Windows 路径、正则、代码）会被不可逆改义，`\\` 只能保护今后按新语法写的数据。违背「存量用户数据逐字节不变」。否决。
- **保存期编解码往返**（弹窗保存时把字面 `\n` 落成真换行、打开时做逆编码保证往返）—— 存量零改动，但引入一门用户要学的转义语法，编辑框显示形态与落库形态不一致，且只在「经弹窗保存」的路径生效（代码或存储直写不保证）。与「能力优先、不新增自定义语法」冲突。否决。
- **上游宿主加 `setCaret` / 带光标参数或 history 选项的 `insertText`** —— 最干净的长期解，但要 DSH 侧改动 + 版本门槛（本仓 `engines.dsh` 仍是 `>=0.2.0-rc.2`，旧宿主仍要降级）。当前不可得，记为将来可替代方案，不阻塞本决定。
- **B. 假 paste 边界 + 保留 `setDraft`** —— 见 §3 修法候选 B：能绕过 undo 组错但引入瞬时草稿变更与 `setDraft` 短路坑，作为 A 的回退项而非常选。当前不启用。
- **只放宽 trim + `{{cursor}}` 两编辑（选定）** —— 只动插件自己的保存与插入两处，不碰存量、不加语法层；标记可见、可解释，旧宿主与引用 chip 全都有降级。
- **完全不做光标、只解码文本** —— 不满足 R2，等于只答半个 issue。否决。

## 后果

- 模板正文可以含开头/结尾空行，插入时逐字符保真；存量一个字节都不变，升级无需迁移。
- 含 `{{cursor}}` 的模板在悬浮列表与智能卡插入后光标精确落位；旧宿主、引用 chip、光标非折叠/坐标不一致、`insertText` 失败、抛错五类路径自动降级（`mode=degraded`）且文本永远正确；`/prompt` 只剥标记、不承诺光标。
- 用户意图的插入一律是可撤销编辑（有标记两笔、无标记一笔），非降级路径不使用 `setDraft`；`check:issue-181` 钉住 undo1/undo2/redo 序列、降级矩阵与源码不变量。
- 插入后第一次撤销可能露出标记文本、第二次撤销回到插入前的草稿（#181 前会连插入前输入一起吞掉）；字面 `{{cursor}}` 暂时无法表达 —— 两条都写进 README（中英同步）。
- 所有展示面永不显示标记：首行简介取第一个非空行、单行预览压空白、搜索与评分用剥标记文本；标记只在「保存正文」这一步有意义。
- 回归与门禁由实施票承接（保存幂等 / 读取面剥标记 / 两编辑成功与四类降级 / `/prompt` 只剥标记）；本 ADR 只钉边界与代价，不钉实现细节。
- 若将来上游补了光标级 API，可把两编辑降为「单编辑 + setCaret」的后备路径；届时应新开 ADR 记录替换，而不是直接删掉本决定的降级阶梯。
