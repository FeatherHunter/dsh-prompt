# 模板颜色标签：用户选的颜色＝用户数据，插件铬色仍全走宿主变量

**状态**：accepted（2026-10-14，地图「每个自定义 prompt 的颜色标签：名字染色 + 深浅主题描边」定稿 + 三条上游票「可读性下限与色板判据」「描边技术与裁切实测」「描边与色板观感对照图」收口；本票落盘。）

## 背景

- 本仓对「颜色」有两条硬口径，两条都是对**插件自己的铬（UI chrome）**说的：[配置页加「作者其他插件」引流区 + 右上角 GitHub/ISSUE 图标按钮](https://github.com/FeatherHunter/dsh-prompt/issues/37) 要求版式「浅色与深色主题都靠宿主变量，不写死颜色」；[设置页更新入口与更新弹窗的版式/信息重做](https://github.com/FeatherHunter/dsh-prompt/issues/60) 要求「不加新视觉概念（不引新色、不引新字号、不引新圆角）」。
- 本次改动带来的新东西是**用户给模板挑的一个颜色**：它把模板名文字染成该色。若把它读成「插件新增了一种颜色」，就直接撞上上面两条；若把它读成**用户数据**，两条口径原封不动。
- 仓库已有这条先例：用户自造的东西（模板名、自选标签）是用户数据，读侧可归一、写侧永原文、翻译永不回写（`docs/adr/0006-locale-identity-and-subscription.md`）。
- 仓库里另有一个「插件自己给颜色」的先例：工作区的身份色点从一个固定色板里自动取（`src/client/workspace.ts:385` 的 `WORKSPACE_DOT_COLORS`）。那是**插件分配的标识色**，不是用户数据。本决定与它并行不悖，两条路不许互相渗透：插件色板不扩成用户可选，用户选的颜色也不收进插件色板。
- 另有两条数学事实把「用户数据的可用域」压窄了（研究票 [可读性下限与色板判据](https://github.com/FeatherHunter/dsh-prompt/issues/155)）：填充色亮度须落在 `L ∈ [0.176, 0.300]`，才能同时对两套主题的底色与黑白描边保持 ≥3:1；sRGB 里只有约 22% 的颜色过得了这条线，且浅色系在「两主题都 AA」上没有公共交集。

## 决定

### 1. 用户给模板选的颜色是**用户数据**，不是插件的颜色

- 它与用户自造标签同类：由用户选定、随模板落盘，**永不翻译、永不改写、不做语义映射**；插件只把它原样透传到名字文字的颜色上。
- 因此 #37 / #60 两条口径继续全额有效，且管的是另一件事：插件自绘的铬（边框、描述色、强调色、气泡、徽标……）不引新色、不新增新造的色值常量。本决定**不为铬新增任何颜色**：本次改动渲染路径上唯一的新颜色就是用户自己那个值（原样显示），再加一个取宿主令牌的描边。既有字面色不属本决定——`var(--dsw-specific-accent,#f0a45c)` / `var(--dsw-specific-danger,#e06c75)` 这类令牌兜底与工作区色点都是早于本决定的历史既有物，本次一个不动。
- 描边色同样不新造：它取宿主令牌（浅色主题下呈近黑、深色主题下呈近白），「深色白描边 / 浅色黑描边」由宿主令牌的翻转白拿，插件不写死 `#fff` / `#000`，也不看系统主题。

### 2. 可读性靠**输入侧约束 + 读侧回落**，绝不靠改写存量

- 取色控件只提供可读带内的深浅：色相自由，明度锁在带内，带外灰掉不可选（控件取的带比上面那条判据再留余量，只窄不宽）。
- 存量数据或外部写入的带外/非法值，在读侧**当作「未选颜色」回落**（跟随宿主主题文字色、恒无描边）。
- 明确否决「读时把用户颜色改写成最近的合法色」：那是对用户数据的改写，与第 1 条冲突；宁可显示成「没选颜色」，也不动用户写的值。

### 3. 「未选颜色」是一个真状态，不是一个颜色

- 它的含义是**跟随宿主**：文字用宿主主题的文字色、恒无描边。所以它的表现天然跟着主题走，与今天逐字节一致。
- 也因此不需要「默认白色」这个值：把默认做成一个具体色值，等于在用户数据里写进一个没人选过的颜色，并让主题跟随失效。

### 4. 不新增主题/配色能力

- 主题跟随纯 CSS（宿主在 `body` 上的主题属性 + 令牌），插件不加 JS 主题检测、不新增 `ctx.theme` 注入、不做插件级配色开关——那是「dsh-opencode-palette」的产品领域。
- 颜色只作用户数据透传，不参与筛选、搜索、排序、召回评分，也不进日志字段白名单（与模板名、正文同级的隐私口径）。

## 考虑过的选项

- **把用户选色当成插件新增的色板**——等于引新色，撞 #37 / #60，且插件从此要管配色（领域错位）。否决。
- **允许任意颜色**——sRGB 里只有约 22% 过 3:1，浅色系在两套主题下没有可用交集，浅色文字在浅色底上必然失读。但「限制输入」与「改写存量」是两件事，只取前者：色相仍任意。否决任意明度。
- **读时把非法值归一/吸附到最近的合法色**——能救存量，但改写了用户数据，且用户看不出被改过。否决，改走读侧回落。
- **把用户选色映射到宿主语义令牌（挑最近的那个）**——用户挑的是一个具体颜色，不是「我同意某个语义色」；映射既要改数据又要长期维护映射表。否决。
- **描边写死 `#fff` / `#000` 配 `@media (prefers-color-scheme: dark)`**——宿主的手动主题与系统主题可以不一致，media query 会答错；写死颜色本身也撞 #60。否决，改取宿主令牌。
- **默认值落成白色**——把「跟随主题」降级成「用户选过白」，主题一翻就露馅，且与「不选颜色＝无描边」这条用户要求对不上。否决。

## 后果

- `CONTEXT.md` 增两条术语：**颜色标签**、**描边**；「标签 (label)」与「颜色标签」的区别写在术语里。
- 三条契约要由后续票守住（「数据层与后端 schema」＋「回归脚本与门禁」承接）：① 存量自定义模板读回**逐字节不变**；② 带外的颜色值读侧回落为「未选颜色」，且**不写回**；③ 本次新增/改动的渲染路径里不出现新造的色值常量，描边色必须是宿主令牌（既有 accent / danger 兜底与工作区色点不在本次范围，也不许借机改动）。
- 后续若要让预制模板上色、或让颜色参与筛选/分组，都属于「把用户数据当结构用」，需要新 ADR 重新划界。
- 颜色的存储形态与后端 schema 补位不在本 ADR：另见票「数据层与后端 schema：可选 color 字段、不迁移、读时回落」。本 ADR 只钉边界，不钉字段实现。
